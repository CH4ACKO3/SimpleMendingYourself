# 修补材料搬运回归检查

## 原因

旧驱动调用 `CollectIngredientsToils(B, C, C)`，把工作台和材料落地点都放在 C。
第一次放料时 `SetTargetToIngredientPlaceCell` 把 C 改为坐标；第二趟
`GotoThing(C, InteractionCell)` 因而不再拿到工作台。用户日志中的
`toilIndex=5` 和 `C = (111, 0, 134)` 与这个流程吻合。

旧驱动在每个收集 toil 结束时保存 `CarriedThing`，会重复记录同一物品，
也无法可靠追踪分堆、合堆后的落地材料。原版放料函数只为特定原版 JobDef
更新 `job.placedThings`，不会自动替自定义的 `SMY_MendSelf` 记录。
源堆的预留也不能覆盖分离出来的新堆。

## 修复约定

- A 始终是待修装备，C 始终是工作台；B 在放料阶段临时存落地点。
- 放料回调用实际落地堆和数量更新 `job.placedThings`，同时建立普通预留和物理交互预留。
- 材料不足、消失、被禁止或放料/预留失败时终止任务，不完成修补。
- 完成时按记录数量 `SplitOff` 后销毁，不销毁合堆中的额外材料。
- `job.placedThings` 使用游戏原生存档机制。新增驱动版本字段；旧版进行中的任务
  缺少该字段，会失效并重新选工作，避免继续使用旧 toil 索引和错误材料记录。
- 任务结束由游戏的正常任务清理流程释放预留；中断不扣除已经落地的材料。

## 游戏内待执行场景

以下是回归步骤，不是已完成的游戏实测结果。

1. 让一名殖民者修补需 150 以上塑钢的装备，材料分散在至少三个堆，另两人优先搬运，
   并设置可接收塑钢的仓库。预期多趟搬运完成、落地材料不被搬走、无 GotoThing 红字。
2. 使用超过单次携带量的一个源堆，确认剩余数量重新入队后仍可完成。
3. 在工作台附近预先放置少量同类材料，使搬来的材料发生合堆；比较修补前后地图总量，
   应恰好减少修补成本，原有额外材料应保留。
4. 第一趟放料后征召修补者；预期装备耐久不变，材料不消耗，其他人可以重新搬运。
5. 在搬运中途、工作进度中途分别保存并重载，确认材料数量和预留保持，修补只结算一次。
6. 载入旧 DLL 保存的进行中修补任务，确认旧任务退出并重新调度，无免费修补或异常。
7. 开发模式删除已落地材料、移除工作台或禁止材料，确认任务停止而不完成修补。
8. 阻塞所有有效落地点，确认任务失败而不是吞掉材料或完成修补。
